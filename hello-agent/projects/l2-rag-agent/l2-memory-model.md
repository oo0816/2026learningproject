## 二、B 线验证问题

### 问 1：对话上下文和长期记忆的实现方式有什么本质不同？
1. 定位不同（最本质的差别）

对话上下文（messages）：是一条按时间顺序的时间线，记录"刚才发生了什么"，状态靠它自己推进。它是过程记录。
长期记忆（long_term）：是一个可检索的知识库，沉淀"什么是重要的、需要一直记住的"，按语义组织而非时间顺序。它是结果沉淀。

2. 存储位置与生命周期

messages 在内存里（一个 Python list），进程一结束就全部消失。
long_term 在磁盘上（JSON 文件），程序关了、明天再打开，记忆还在。

3. 数据形态

messages 是原始消息链（role + content + tool_calls），不加工、顺序即语义。
long_term 是结构化条目（id / content / tags / source / created_at），是经过提取整理后的信息，还带元数据方便检索。

4. 读写时机与成本

messages：每次调用全量发给 LLM，对话推进就 append。token 是钱，所以太长必须裁剪。
long_term：触发式写入（模型回复里嵌 [[REMEMBER]] 标签才写），检索式读取（只把相关的那几条注入 system prompt），不占 messages 位置，体积可控。

5. 信息丢失的代价

messages 被裁剪 = 信息真的丢了（只能靠 session 层备份补救）。
long_term 在磁盘上，裁剪 messages 不影响它——这是它存在的意义。

### 问 2：向量检索返回了不相关的结果，agent 应该怎么处理？

答：分「检索层过滤」和「agent 层兜底」两层

第一层：检索时先过滤噪声（L2 已实现）

相似度阈值：search() 里 score < 0.1 就丢弃，低分的一律不算结果。
top-K 限制：
只保留最相关的 3 条，不让垃圾淹没模型。
升级方向：
纯向量对"精确匹配"不敏感，成熟系统用关键词 + 向量的混合检索，精确命中和语义相关互补。

第二层：
agent 层兜底（核心）——检索结果是"候选材料"，不是"答案"

这层的关键认知：RAG 检索出来的东西只是参考资料，agent 要负责判断它相不相关，而不是照单全收。

具体行为：

相关 → 引用回答：用检索内容作答，并标注来源（（来源：xxx.txt）），让用户知道答案出处、能溯源。
不相关 → 丢弃，用自己的知识回答：不要硬编造一个基于不相关材料的答案。L2 的 system prompt 里已经写了这条规矩——"如果知识库没有相关内容，就用你自己的知识回答"，这就是兜底机制。
明确告诉用户结果：如果检索没找到、或找到的不相关，要诚实说明"知识库没搜到相关内容，以下是基于我自身知识的回答"，而不是假装有依据。

第三层：反馈与改进（面试加分项）

不相关结果多，往往不是 agent 的问题，而是 RAG 管线的问题，要往上游排查：

query 表述问题 → 让模型改写 query 再检索一次（改写扩展：同义词、更具体的描述）。
分块问题 → 块太大混入无关信息，块太小语义不完整。
阈值问题 → 调高相似度阈值，或换更强的 

embedding 模型。
一句话总结：向量检索返回什么由检索层决定，但采不采用由 agent 判断——相关就引用并标注来源，不相关就丢弃、用自己的知识兜底，并且让用户知道信息来源是否可靠。
