Docker 与 Kubernetes（K8s）并非竞争替代关系，而是处于不同层级的协作关系：Docker 是负责单个容器构建、打包与运行的容器引擎，K8s 则是在集群层面对大量容器进行调度、部署与治理的编排平台。二者的关系可以概括为"单机容器"与"集群编排"的上下层互补。理解这一关系的两个关键支点是 CRI（容器运行时接口）与 OCI（镜像与运行时规范）。

## 定位不同、层级不同

Docker 是容器引擎/容器运行时，主要解决"怎么把一个应用装进容器并跑起来"，核心能力包括镜像构建（build）、打包、分发和运行。Kubernetes 是容器编排平台，负责在集群层面对大量容器进行调度、部署、扩缩容、自愈以及网络和存储管理。二者不是同类工具的竞争，而是上下层关系：Docker 面向单机单容器，K8s 面向多机集群。

## 典型的合作关系

在实际工程中，Docker 与 K8s 高度互补。Docker 解决了容器的构建与运行问题，但面对生产环境的多机部署、高可用、滚动更新等需求，仅靠 docker run 或 docker-compose 这类单机工具不足以支撑生产级大规模部署，这正是 K8s 补位的价值所在。K8s 早期默认使用 Docker 作为容器运行时，由此形成了"K8s 编排 + Docker 运行"的经典组合。

## 运行时解耦：CRI 的引入

K8s 引入了 CRI（Container Runtime Interface，容器运行时接口）作为抽象层：理论上只要某个运行时实现了 CRI，就能被 K8s 调度使用，因此不必绑定 Docker。这一设计为后续切换默认运行时奠定了技术基础。除 Docker 外，可选运行时还包括 containerd、CRI-O 等。

## "K8s 弃用 Docker"的真相

Kubernetes v1.24 移除了 dockershim，即不再通过内置垫片直接调用 Docker Engine，转而默认使用 containerd。原因是 Docker Engine 本身不原生实现 CRI 标准，需要 dockershim 作为转换层，维护成本较高。需要澄清的是，这并不意味着"K8s 杀死了 Docker"，而只是不再把 Docker Engine 当作运行时直连。用 Docker 构建出的镜像仍然完全兼容，因为 Docker 镜像本身就是 OCI 格式，containerd 同样可以运行——改变的只是"用谁跑容器"，而不是"用什么造镜像"。

（说明：Kubernetes v1.24 于 2022 年 5 月发布、正式移除 dockershim，属于研究摘要中经检索确认的内容；但"2022 年 5 月 3 日"这一准确日期为知识补充，建议使用前再核实具体版本发布日期。）

## 技术谱系与生态

containerd 最初是从 Docker 项目中拆分出来的核心运行时组件，后捐赠给 CNCF，因此 containerd 与 Docker 是同源后代。二者的侧重不同：Docker 更偏开发者体验（CLI、build、compose），containerd 更偏底层运行时。在生态层面，Docker 曾是容器的事实标准，K8s 后来成为编排的事实标准，两者都在 CNCF/OCI 生态中持续演化。

## 关键视角与典型场景

从视角上看，开发与学习阶段 Docker 已经足够（docker build/run/compose），而生产规模化则需要 K8s 提供调度、自愈、服务发现与声明式管理。一个常见的类比是：Docker 相当于单台机器上的"进程管理"，K8s 相当于"数据中心的操作系统"，管理成百上千个容器与节点。典型例子是：一个 Web 服务先用 Docker 打包成镜像并在本地跑通，上线时用 K8s 声明一个 Deployment，即可实现多副本、故障重启、按负载扩缩容与滚动升级。此外，镜像来源与运行时可分离——即便不用 Docker Engine 做运行时，仍可用 Docker 命令构建镜像，甚至用 Podman、Buildah 等替代 Docker 做构建。

## 结论

Docker 与 K8s 是层级不同、彼此互补的两类工具：前者负责把应用装进容器并跑起来，后者负责在集群层面大规模地编排这些容器。CRI 与 OCI 是理解二者解耦的技术基石，而 K8s v1.24 移除 dockershim、默认改用 containerd，只是运行时的替换，并不影响 Docker 镜像的兼容性，更谈不上"K8s 杀死 Docker"。对使用者而言，选择取决于场景：开发与学习阶段用 Docker 足矣，生产规模化部署则应交由 K8s 完成。
