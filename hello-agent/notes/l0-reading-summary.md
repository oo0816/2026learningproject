# L0 补充：两篇核心文章总结

---

## Anthropic《Building Effective Agents》(2024.12)

作者：Erik Schluntz & Barry Zhang

### 核心哲学：简单至上

最成功的实现用的是简单、可组合的模式，不是复杂框架。很多需求一个 LLM 调用 + 检索就够了。**先问自己：真的需要 agent 吗？**

Agent 系统的代价是延迟和成本——用这些换更好的任务表现，要判断值不值得。

### Workflow vs Agent

| Workflow | Agent |
|----------|-------|
| 代码预定义的执行路径 | 模型自己决定过程和工具使用 |
| 适合明确分解的固定任务 | 适合开放、不可预测的问题 |

### 五种 Workflow 模式（由简到繁）

1. **Prompt Chaining**：任务分解为顺序步骤，前一步输出是下一步输入。例：写大纲→写正文→检查标准
2. **Routing**：分类输入，分发给专门处理器。例：退款请求路由到退款流程，技术支持路由到帮助流程
3. **Parallelization**：多个 LLM 调用并行执行。分两种——拆解独立子任务 / 多轮投票增加置信度
4. **Orchestrator-Workers**：中央 LLM 动态分派任务给 worker，汇总结果。适合无法提前预测子任务的场景（如跨多文件代码改动）
5. **Evaluator-Optimizer**：一个生成→另一个评估反馈→循环改进。例：文学翻译润色

### 真正的 Agent 什么时候用？

- 问题步骤数不可预测、路径无法硬编码
- 需要信任模型的决策能力
- 需要 sandbox 测试 + 护栏（成本高、错误可能累积）

### 三条设计原则

1. 保持简单
2. 让 agent 的计划步骤透明可见
3. 像设计人机交互（HCI）一样设计 Agent-Computer Interface（ACI）——认真写工具文档

### 关于框架

不建议一上来就套 LangChain 等框架。**从直接 API 调用开始**，很多模式就几行代码。框架增加抽象层，让调试变难。

## OpenAI《A Practical Guide to Building Agents》(2025.4)

### Agent 三要素

| 组件 | 职责 |
|------|------|
| **Model** | 推理和决策的大脑 |
| **Tools** | 外部能力——API、数据库、搜索 |
| **Instructions** | 行为约束和护栏 |

### 什么时候该用 Agent？

1. **复杂决策**——需要细微判断、处理例外（如退款审批）
2. **规则难以维护**——规则集庞大、脆弱、更新成本高（如供应商安全审查）
3. **依赖非结构化数据**——自然语言、文档、对话（如保险理赔）

### 七条核心建议

1. **模型选择**：先上最强模型（如 GPT-4o）建立基准，确认可行后降级到更快更便宜的模型
2. **工具三类**：数据工具（检索上下文）/ 行动工具（发邮件、更新记录）/ 编排工具（agent 作为其他 agent 的工具）
3. **指令设计**：用已有的操作手册做素材 → 让 agent 拆解任务 → 每步明确措辞和工具调用 → 覆盖边界情况
4. **编排**：单 agent 起步，加工具逐步迭代。多 agent 只在逻辑太复杂时才拆
5. **多 Agent 两种模式**：Manager（中央调度专家）/ Decentralized（agent 之间直接握手传递）
6. **护栏分层**：相关度分类器 → 安全分类器 → PII 过滤器 → 工具风险分级 → 高危操作人工确认
7. **人在回路**：错误、边缘情况、高风险操作必须有升级路径

### 迭代策略

选一个明确流程 → 单 agent 原型 → 加护栏 → 真实场景测试 → 需要时才扩展多 agent

## 两篇文章的共同点

| 共识 | 说明 |
|------|------|
| 简单起步 | 不要一上来就多 agent、复杂框架 |
| Agent ≠ 万能 | 很多场景 workflow 或单次 LLM 调用更好 |
| 护栏是必需品 | 没有安全机制的 agent 是 demo，不是产品 |
| 人在回路 | 高风险操作必须有人工确认 |
| 评测先行 | 没有 eval 就没有改进方向 |
